# Modules

这个目录记录 EchoWhale 的模块级工作。模块以业务能力为顶层，不以单纯代码层作为唯一划分标准。

## 这里放什么

- `platform_foundation/`：公共底座、配置、共享依赖
- `media_upload/`：图片上传、媒体元数据、对象存储 URL
- `scene_engine/`：图片场景理解
- `coach_engine/`：对话生成与角色推进
- `feedback_engine/`：学习反馈与纠错
- `session_orchestration/`：会话编排与状态管理
- `history_review/`：历史查看与回放
- `frontend_app/`：前端页面与交互壳
- `infra_delivery/`：部署与交付

## 每个模块的标准结构

- `status.md`：模块目标、当前状态、代码位置、测试门和阻塞项
- 需要时再在模块文档里链接实际代码目录、feature 文档和 bug 文档

## 书写原则

- 只写模块级内容，不把 feature 级细节塞进模块总览
- 一个模块只服务一个清晰目标，避免跨模块耦合
- 先定义输入输出契约，再补实现细节
- 如果模块已经能跑通最小流程，就把状态写进对应的 `status.md`

## 当前仓库状态

- `api/modules/` 已经存在，说明后端 scaffold 已经搭好
- 现在更适合补“模块职责、状态、边界”和最小测试，而不是做大规模重构
- 前端和测试体系还弱，所以模块文档要尽量直接、可执行、便于后续接手

## 交接要求

- 新增模块时，先补目录职责说明，再补状态记录
- 任何会改变模块边界的调整，都要先更新这里的说明
- 不要把实验性想法放进正式模块目录，先用 feature 文档隔离
